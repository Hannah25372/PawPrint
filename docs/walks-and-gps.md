# Walks & GPS Tracking

How PawPrint records, stores, processes and serves walk routes.

## Decisions at a glance

| Area | Decision |
|---|---|
| Recording | Mobile app (Expo / React Native). Web (Next.js) is view-only. |
| Database | PostgreSQL + PostGIS on AWS RDS |
| Raw GPS tracks | Compressed files in S3, never served to anyone but the owner |
| Display routes | Simplified `LineString` geometry in Postgres |
| Upload | Whole track uploaded once at the end of a walk, idempotent |
| Processing | Synchronous inside the upload request (for now) |
| Privacy | User-defined privacy zones, clipped at write time |

## Why not S3 + NoSQL (the Strava approach)?

Strava's split exists to handle billions of activities. PawPrint's data is mostly relational: dogs with many owners, follows, friends, walks linked to dogs, and visibility rules evaluated against the follow graph. A document store makes all of that harder.

PostgreSQL + PostGIS gives us both:

- Relational integrity and joins for visibility and the feed
- Spatial types and functions: `ST_Length(geography)` (distance), `ST_Simplify` (display routes), `ST_Difference` (privacy clipping), and later proximity queries ("walks near me")
- First-class EF Core support via `Npgsql.EntityFrameworkCore.PostgreSQL.NetTopologySuite`, so a route is a `LineString` property on the entity

We do borrow one idea from Strava: raw GPS points live in object storage (S3), not in database rows.

## Recording (mobile app)

Browsers cannot reliably record GPS with the screen locked (iOS Safari suspends `watchPosition`), so recording is mobile-only.

- **Stack:** Expo with `expo-location` + `expo-task-manager` for background location
- **iOS:** `UIBackgroundModes: location` and "Always" permission, with a clear usage string ("records your walk route")
- **Android:** foreground service with an ongoing "Walk in progress" notification
- **Sampling:** high accuracy, `distanceInterval` of about 5 m. Distance-based rather than time-based, because dogs stop a lot and time-based sampling wastes points.
- **Durability:** every fix is written to on-device SQLite (`expo-sqlite`) as it arrives, so walks survive the app being killed or the phone dying
- **Upload:** once, at walk end. The app generates the walk ID (UUID) so retries are idempotent. The walk stays queued locally until the server acknowledges it.

## Storage model

| Data | Location | Purpose |
|---|---|---|
| Raw track (lat, lon, elevation, timestamp, accuracy per point) | S3: `tracks/{userId}/{walkId}.json.gz` | Source of truth. Owner-only. Allows reprocessing. |
| Processed route | `walks.route` (`geometry(LineString, 4326)`) | Cleaned and simplified. Map display for the owner. |
| Public route | `walks.public_route` | `route` with privacy zones clipped out. Served to everyone else. |
| Metadata | Columns on `walks` | Feed, profile, stats |
| Photos | S3, uploaded directly from the app via presigned URLs | Referenced from `walk_photos` |

At one point per second, a one-hour walk is about 3,600 points. Storing those as rows would grow to hundreds of millions of rows quickly. A compressed track file is roughly 30–100 KB.

Application declares an `ITrackStorage` interface. Infrastructure implements it with S3 (or MinIO for local dev). Use cases never talk to S3 directly.

### Schema sketch

```
users(id, username, bio, avatar_url, ...)
dogs(id, name, breed, birth_date, temperament, photo_url)
dog_owners(dog_id, user_id, role)                  -- many-to-many
walks(id, user_id, started_at, ended_at,
      distance_m, moving_s, elapsed_s, elevation_gain_m,
      visibility, notes,
      route, public_route, raw_track_key, processing_version)
walk_dogs(walk_id, dog_id)
walk_photos(id, walk_id, s3_key, taken_at, location)
follows(follower_id, followee_id, created_at)
privacy_zones(id, user_id, center geography(Point), radius_m)
```

- `walks.id` is generated by the client (see Recording)
- Index `walks(user_id, started_at DESC)` for the profile and feed queries

## Upload & processing flow

```
App ── POST /walks  (walk id, metadata, compressed track, dog ids) ──► API
                                                                      │
   1. Store raw track in S3                                           │
   2. Process: filter noise → detect pauses → distance/moving time    │
   3. Build route (simplified) + public_route (privacy zones clipped) │
   4. Insert walk + walk_dogs in one transaction                      │
App ◄──────────────────────── 201 + WalkDto ─────────────────────────┘
```

If a walk ID already exists for that user, return the existing walk (idempotent retry).

### Processing steps

1. **Filter noise:** drop fixes with poor horizontal accuracy (e.g. worse than 30 m) and impossible jumps (implied speed far above walking pace). Lightly smooth. Raw phone GPS overstates distance by roughly 5–15%.
2. **Detect pauses:** dog walks are mostly stopping (sniffing, greeting, poop bags). Track **moving time** separately from **elapsed time**, and compute pace from moving time.
3. **Compute stats:** distance via `ST_Length(route::geography)`, moving and elapsed time, elevation gain.
4. **Elevation:** phone GPS altitude is poor. Low priority. Later options are the barometer on device, or correction against a terrain elevation dataset on the server.
5. **Simplify:** `ST_Simplify` for the stored display route.
6. **Privacy:** produce `public_route` (see below).

Stamp each walk with `processing_version`, so walks can be reprocessed from raw S3 tracks when the algorithm improves.

## Privacy

- **Privacy zones**, not fixed trims. Users define circles (e.g. around home), and any part of a route inside a zone is removed from `public_route`. Fixed "trim the first and last N metres" is easy to undo: many walks ending 200 m from the same spot point to the house.
- **Raw tracks and `route` are owner-only.** Every non-owner response uses `public_route`.
- **Metadata leaks too.** Exact start times plus a route reveal routines. Consider rounding start times on public walks.
- **Visibility (private / followers / public) is enforced in one place**: a single query or specification in Application, not per endpoint.

## Feed

Built at read time: walks where `user_id` is in the people I follow and visibility allows, ordered by `started_at DESC`, with cursor pagination. With the index above, this holds up for a long time.

## AWS infrastructure

| Piece | Service | Notes |
|---|---|---|
| Database | RDS PostgreSQL + PostGIS | Smallest Graviton instance (`db.t4g.micro`). Likely the largest cost. |
| Tracks & photos | S3 | Presigned URLs for photo uploads from the app |
| API | One Docker container on Lightsail / EC2, or ECS Fargate | |

**Avoid NAT Gateways.** Guides for Fargate or Lambda in private subnets often add one. It costs about $30+/month even when idle. Use public subnets with tight security groups, or a VPC gateway endpoint for S3.

**Local dev:** `postgis/postgis` Docker image via `docker-compose`. Use MinIO or a dev S3 bucket behind `ITrackStorage`.

## Scaling: now vs later

**Do now** (cheap, and painful to add later):

- Keep raw tracks unchanged in S3
- `processing_version` on walks
- Client-generated walk IDs and idempotent uploads
- `ITrackStorage` and a standalone processing service in Application, so processing can move to a worker unchanged

**Defer** until there is real load:

- Async processing (SQS + worker)
- CDN for photos and map tiles
- Read replicas and feed caching
- Precomputing each user's feed when a walk is posted
